## Reikwijdte

Deze instructies gelden voor:

`2. Toepassing`

Pas daarnaast altijd `1. Algemeen.md` toe.

Bij toepassingen van data science, machine learning en AI gelden ook de relevante terminologie- en opmaakregels uit `3. Data science.md`.

## Doel

`2. Toepassing` beschrijft hoe concepten praktisch worden toegepast met programmeertalen, libraries, frameworks en tools.

De nadruk ligt op:

`wat wil ik doen? → wat gebeurt er conceptueel? → hoe doe ik dit praktisch?`

Een toepassingspagina moet vooral helpen begrijpen **wat code of een tool doet en hoe dit samenhangt met de concepten uit** `**1. Concepten**`.

Bouw geen vervangende API-documentatie.

## Relatie met `1. Concepten`

- Gebruik bestaande concepten uit `1. Concepten` als theoretische basis.
    
- Verwijs waar relevant met Obsidian-links naar deze concepten.
    
- Dupliceer de theoretische uitleg van gelinkte concepten niet.
    
- Leg wel uit hoe deze concepten zich manifesteren in de concrete library, functie, class of tool.
    
- Als meerdere praktische onderdelen terug te voeren zijn op hetzelfde concept, link dan naar dat concept in plaats van de uitleg opnieuw te geven.
    

Een pagina over bijvoorbeeld `RandomForestClassifier` legt dus niet opnieuw volledig uit wat een random forest is, maar verwijst naar het bestaande concept en beschrijft hoe scikit-learn dit praktisch beschikbaar maakt.

## Structuur

Groepeer praktische onderwerpen primair op:

1. doel;
    
2. toepassing;
    
3. probleem dat wordt opgelost.
    

Gebruik alleen een library-, framework- of toolgerichte structuur wanneer het onderwerp daadwerkelijk specifiek is voor die technologie.

Binnen een library-specifieke structuur mogen concrete classes of functies verder worden gegroepeerd op hun primaire toepassing, bijvoorbeeld:

```
scikit-learn/
├── 0. Basisbegrippen/
└── 1. Estimators/
    ├── 1. Classification/
    ├── 2. Regression/
    ├── 3. Clustering/
    └── 4. Preprocessing/
```

Een class kan meerdere rollen of capabilities hebben. Deel concrete classes daarom niet uitsluitend in op interfaces zoals _predictor_ of _transformer_ wanneer deze rollen elkaar kunnen overlappen.

Bekijk vóór een nieuw bestand of een nieuwe map wordt voorgesteld altijd eerst de bestaande repositorystructuur.

Geef bij een voorstel altijd het volledige pad.

## Detailniveau

Houd toepassingspagina's compact.

Neem alleen informatie op die nodig is om:

1. te begrijpen waarvoor de functie, class of tool wordt gebruikt;
    
2. te begrijpen wat er conceptueel gebeurt;
    
3. de relatie met relevante concepten uit `1. Concepten` te herkennen;
    
4. de belangrijkste output correct te interpreteren;
    
5. relevante verschillen met vergelijkbare mogelijkheden te begrijpen.
    

Neem niet automatisch alle parameters, attributen, methods of configuratieopties op.

Een parameter of functionaliteit is vooral relevant wanneer deze:

- bepaalt **wat voor model, transformatie of gedrag** ontstaat;
    
- nodig is om de output te begrijpen;
    
- een fundamentele capability van de class of functie weergeeft;
    
- regelmatig nodig is om het beschreven doel te bereiken.
    

Een parameter die alleen een verdere configuratie van hetzelfde mechanisme vormt, hoeft meestal niet te worden opgenomen.

Bij `SGDClassifier` is `loss` bijvoorbeeld relevant omdat deze mede bepaalt welk type lineair classification model wordt geleerd. Bij `RandomForestClassifier` hoeven parameters zoals `bootstrap` of `max_features` niet alleen vanwege hun bestaan te worden beschreven.

## Uitleg

Leg vooral uit **wat er gebeurt**.

Gebruik waar nuttig een korte procesweergave, bijvoorbeeld:

```
estimator
    ↓
fit()
    ↓
getraind model
    ↓
prediction op validation fold
    ↓
performance score
```

Maak onderscheid tussen:

- het praktische softwareobject;
    
- de methode die daarop wordt aangeroepen;
    
- het onderliggende concept;
    
- de output die daaruit ontstaat.
    

Bijvoorbeeld: `cross_val_predict(method="predict_proba")` vraagt niet abstract om "probabilities", maar roept voor iedere getrainde estimator `predict_proba()` aan op de validation fold. De gekozen methode bepaalt vervolgens welk type output wordt teruggegeven.

## Code

Gebruik fenced code blocks met waar relevant de juiste taalidentifier.

Voor Python:

```python
from sklearn.linear_model import LogisticRegression
```

Voor conceptuele schema's:

```
training data
    ↓
fit()
    ↓
model
```

Houd code zo klein mogelijk.

- Toon alleen code die nodig is om het onderwerp te begrijpen.
    
- Gebruik bij eenvoudige pagina's over een Python-class bij voorkeur alleen de relevante `import` wanneer constructie, `fit()` en standaardgebruik vanzelf spreken.
    
- Voeg aanvullende code alleen toe wanneer deze nodig is om een conceptueel relevant verschil of gedrag te laten zien.
    
- Gebruik geen volledige scripts wanneer een kleiner fragment voldoende is.
    
- Gebruik commentaar alleen wanneer de betekenis niet direct uit de code en omliggende uitleg blijkt.
    

## Functies en methods

Beschrijf bij functies en methods:

1. wat ze doen;
    
2. wat er conceptueel tijdens uitvoering gebeurt;
    
3. welke relevante input het gedrag bepaalt;
    
4. welke output wordt teruggegeven.
    

Behandel alleen parameters die daarvoor nodig zijn.

Pagina's zoals `cross_val_score()` en `cross_val_predict()` gelden als uitgangspunt voor het gewenste detailniveau.

Beschrijf bijvoorbeeld bij `cross_val_predict()` waarom iedere observation een out-of-fold output krijgt en wat `method` conceptueel bepaalt, maar bouw geen overzicht van alle mogelijke parameters van `cross_val_predict()`.

## Classes

Beschrijf bij een concrete class eerst kort:

- wat voor scikit-learn-, library- of frameworkobject het is;
    
- welk bestaand concept ermee wordt geïmplementeerd;
    
- wat het object praktisch mogelijk maakt.
    

Voor een eenvoudige scikit-learn-class kan daarna een compacte tabel worden gebruikt.

Bijvoorbeeld:

|Eigenschap|Class|
|---|---|
|**Transformer**|-|
|**Predictor**|type output via relevante method|
|Modeltype|onderliggend model|
|Multiclass|wijze waarop meerdere classes worden ondersteund|
|`decision_function()`|type output, indien beschikbaar|
|`predict_proba()`|type output en eventuele voorwaarden|
|`partial_fit()`|relevante functionaliteit of `-`|

Gebruik `-` wanneer een opgenomen eigenschap of functionaliteit niet wordt ondersteund of niet van toepassing is.

Neem alleen rijen op die voor de betreffende class relevant zijn.

Voeg relevante parameters of attributen alleen toe wanneer deze noodzakelijk zijn om de werking van de class te begrijpen.

## Terminologie

Gebruik bij toepassingen van data science, machine learning en AI de gangbare Engelse technische termen als primaire termen, overeenkomstig `3. Data science.md`.

Gebruik dezelfde technische term consequent in:

- titels;
    
- bestandsnamen;
    
- tabellen;
    
- uitleg;
    
- voorbeelden.
    

Vertaal bestaande technische termen uit `1. Concepten/2. Data science` niet opnieuw naar het Nederlands.

Gebruik voor de eerste relevante vermelding van een bestaand concept een Obsidian-link.

Zet technische Engelse termen cursief wanneer dit volgens de opmaakregels van `3. Data science.md` van toepassing is.

## Output en interpretatie

Beschrijf waar relevant niet alleen **wat** een functie retourneert, maar ook **wat die output betekent**.

Maak bijvoorbeeld onderscheid tussen:

- _class prediction_;
    
- _decision score_;
    
- _estimated probability_;
    
- _performance score_;
    
- getransformeerde data.
    

Verwijs hiervoor waar mogelijk naar de bestaande definities in `1. Concepten`.

## Meerdere oplossingen

Wanneer meerdere functies, classes, libraries of technieken hetzelfde doel dienen:

- beschrijf eerst het gedeelde doel;
    
- benoem daarna de conceptueel relevante verschillen;
    
- voorkom herhaling van dezelfde theorie;
    
- gebruik een tabel wanneer de verschillen daarmee duidelijker worden.
    

Vergelijk alleen eigenschappen die voor de praktische keuze relevant zijn.
