## Reikwijdte

Deze instructies gelden voor:

`2. Toepassing`

Pas daarnaast altijd `1. Algemeen.md` toe.

Bij toepassingen van data science, machine learning of AI geldt waar relevant ook de terminologie uit `3. Data science.md`.

## Doel

`2. Toepassing` beschrijft hoe concepten praktisch worden toegepast met programmeertalen, libraries, frameworks en tools.

Structureer vanuit:

`wat wil ik doen? → welke oplossingen bestaan? → hoe gebruik ik deze?`

Niet vanuit de volledige API of functieset van een specifieke library.

## Structuur

- Groepeer onderwerpen primair op doel, handeling of probleem.
- Plaats verschillende libraries die hetzelfde probleem oplossen bij voorkeur op dezelfde pagina.
- Gebruik alleen een library- of toolgerichte structuur wanneer het onderwerp daadwerkelijk specifiek is voor die library of tool.
- Bekijk vóór een nieuw bestand wordt voorgesteld eerst de bestaande repositorystructuur.
- Geef altijd het volledige voorgestelde pad.

## Relatie met concepten

- Leg kort uit welk praktisch probleem of concept centraal staat.
- Verwijs waar relevant met Obsidian-links naar `1. Concepten`.
- Dupliceer bestaande conceptuele uitleg niet.

## Pagina-opbouw

Gebruik waar relevant deze volgorde:

1. Onderwerp en korte uitleg
2. Voorbeelddata
3. Oplossing(en)
4. Uitleg van relevante parameters
5. Vergelijking van oplossingen
6. Interpretatie en aandachtspunten
7. Officiële documentatie

Laat onderdelen weg wanneer ze geen toegevoegde waarde hebben.

## Definities

Als het praktische onderwerp zelf een bruikbaar begrip vormt, gebruik dan een library-onafhankelijke `info`-callout.

Plaats library-specifieke uitleg daarna in afzonderlijke secties.

## Code

- Gebruik fenced code blocks met de juiste taal.
- Houd voorbeelden klein, actueel en zelfstandig begrijpelijk.
- Toon alleen code die relevant is voor het onderwerp.
- Gebruik commentaar alleen wanneer een stap niet direct uit de code blijkt.
- Geef inhoudelijke uitleg bij voorkeur in de Markdown rondom het codeblok.
- Vermijd volledige scripts wanneer een klein fragment voldoende is.

## Voorbeelden

- Plaats volledige voorbeelden waar passend in een uitklapbare `example`-callout.
- Kleine codefragmenten die slechts één parameter of syntactisch detail demonstreren mogen buiten een callout staan.

## Parameters en argumenten

- Leg parameters uit die belangrijk zijn voor begrip of regelmatig gebruik.
- Beschrijf niet de volledige API wanneer die informatie in de officiële documentatie staat.

## Meerdere oplossingen

Wanneer meerdere libraries of technieken hetzelfde probleem oplossen:

- beschrijf eerst het gedeelde doel of concept;
- geef daarna per oplossing de relevante code;
- benoem praktisch relevante verschillen;
- voorkom herhaling van dezelfde uitleg.

Gebruik een tabel wanneer oplossingen zinvol naast elkaar kunnen worden vergeleken.

## Interpretatie

Leg waar relevant naast het gebruik van de code ook uit hoe de output moet worden geïnterpreteerd en welke conclusies er wel of niet uit mogen worden getrokken.

Verwijs voor onderliggende theorie naar `1. Concepten`.

## Documentatie

- Voeg waar relevant links naar officiële documentatie toe.
- Geef officiële documentatie voorrang boven blogs en tutorials.

## Detailniveau

Een toepassingspagina bevat genoeg informatie om:

1. te begrijpen waarvoor de techniek dient;
2. de belangrijkste code opnieuw te kunnen schrijven;
3. relevante parameters te herkennen;
4. de output te interpreteren;
5. verdere details in de officiële documentatie te vinden.

Maak geen volledige API-reference.
